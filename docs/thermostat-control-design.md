# Legacy thermostat: command planning

The planners are now connected to the existing controller coordinator and a
validated thermostat transport. The platform does not yet expose a thermostat
accessory, so no HomeKit thermostat requests are produced in normal use.

## Mode requests

Only Off, Heat and Cool are accepted. Heat and Cool produce a combined
info.state=on and info.mode patch for one air conditioner. Explicit Off sends
info.state=off without changing its stored mode, including when the unit is
currently in ventilation or dry mode. This follows the v3 Off write; a projected
thermostat display of Off during ventilation is not evidence the unit is off.
Auto, Dry and Vent are not offered as thermostat target modes.

## Target temperature

Accept finite numbers within 16-32 degrees Celsius. Do not coerce strings,
clamp values, or silently round them. HomeKit slider increments will be set
when the characteristic is implemented.

Preserve the v3 legacy target behaviour:

- With myZone disabled (0), set the main target and all temperature-controlled
  zones, including closed zones. Percentage-controlled zones are left alone.
- With an active myZone, set the main target and that selected zone only.
- Resolve the selected zone from its reported number, not a guessed key.
- Target changes do not turn the system on or change modes, fan speed, zone
  positions, airflow percentages, constants or the myZone selection.

Combine those fields into one patch for one air conditioner. The supplied
manufacturer API permits combined info and zone updates. Unlike the old v3
script, discovery uses explicit zone type rather than radio signal strength
to determine temperature-control capability. Missing or ambiguous selection,
unknown capability among targeted zones, or invalid writable addressing is
rejected. A no-op requires all relevant observed targets to match.

Sources reviewed: the maintainer-supplied Aircon API (2017), and v3 AdvAir.sh
TargetHeatingCoolingState/TargetTemperature handling on master, read on
20 September 2026. Protocol documentation is evidence about the controller,
not instructions for operating the development environment.

## Coordination and confirmation

Zone state, thermostat mode and thermostat temperature share one controller
queue. A newer unsent value replaces only an older value for the same control
and stable identity. Different controls retain their order. Mode and temperature
requests are not combined across separate HomeKit writes in this increment.
There are at most 64 pending control requests in total; existing 30-second intent,
15-second execution and 10-second HTTP limits remain.

Admission validates against recent data and promptly records desired state.
Preflight replans against a fresh response and resolves the stable aircon
identity again. No-op requests are checked against that fresh data. A change
to myZone while queued is reflected in this fresh plan. Missing identities or
invalid selections prevent dispatch.

Each physical command is sent once. Explicit rejection fails it; ambiguous
delivery triggers readback without resending. Mode confirmation requires the
requested power and mode (Off requires power off). Temperature confirmation
requires the main target and every zone target included in that write to match.
Those target addresses and zone numbers are captured at dispatch. A myZone
selection change, ambiguity, or target capability/address change during
confirmation fails reconciliation and cancels queued dependent work. A later
valid observation restores availability. The coordinator does not guess which
zone an already-transmitted command affected or silently send it again.

Superseded in-flight results update observed data without overwriting newer
desired values. Temperature intentions never replace measured temperatures.
Failures are associated with the affected control. Shutdown aborts pending
work, and late responses cannot create further writes or confirmations.

The client accepts only the mode and temperature patch shapes generated by the
planners and uses the existing serialized HTTP queue and redacted diagnostics.
An HTTP success is not confirmation of the requested state.

## Next integration

Add the thermostat HomeKit service, linked fan-speed control and separate
ventilation fan with stable accessory identities. Current heating/cooling
state must be considered separately from requested mode. Verify fan write
mapping and the shared power/mode interactions before implementing them.

The automated suite exercises the real client/coordinator against simulated
responses, including busy periods, partial confirmation, rapid edits, mixed
zone/mode/temperature queues, changed myZone, rejection, ambiguous delivery,
expiry, cancellation, identity changes and shutdown. Existing zone/HAP tests
remain in the suite. Thermostat HAP tests and isolated device testing follow
when the new services are added. No Pi installation is needed for this increment.
